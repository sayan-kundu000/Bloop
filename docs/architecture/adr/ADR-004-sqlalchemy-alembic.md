# ADR-004: Selection of SQLAlchemy 2.0 and Alembic for ORM and Schema Migrations

## Status
**Accepted**

## Context
Interacting with PostgreSQL requires an Object Relational Mapper (ORM) that prevents SQL injection, maps database rows to Python domain models, manages database connection pools, and tracks transactional state. Furthermore, evolving database schemas across development, staging, and production requires a deterministic, version-controlled migration tool.

## Decision
Adopt **SQLAlchemy 2.0+** as the persistence ORM and **Alembic 1.13+** as the automated database schema migration manager.

## Alternatives Considered
1. **Raw SQL with `psycopg2` / `asyncpg`:** Maximizes raw execution performance, but eliminates object abstraction, requires verbose manual SQL construction, increases vulnerability to SQL injection vulnerabilities, and lacks schema tracking.
2. **Tortoise ORM / Peewee:** Async-first ORMs, but have smaller communities, less comprehensive documentation, and far fewer enterprise production battle-tested migration tools compared to SQLAlchemy + Alembic.
3. **Prisma (Python Client):** Elegant schema definitions, but the Python client is less mature, relies on an external Rust engine binary, and adds unnecessary operational friction in Python container deployments on Render.

## Consequences

### Positive
- **Type-Safe 2.0 Syntax:** Modern SQLAlchemy 2.0 `Mapped[...]` and `mapped_column()` annotations provide complete static typing integration with Mypy and IDE autocompletion.
- **Automated Migration Generation:** Alembic detects differences between Declarative Base models and the current database state (`alembic revision --autogenerate`), generating deterministic, reversible migration scripts in `backend/alembic/versions/`.
- **Zero-Downtime Deployment Command:** Render executes `alembic upgrade head` automatically during the pre-deploy build hook, guaranteeing that the database schema is synchronized before the new FastAPI process accepts traffic.
- **SQL Injection Prevention:** Parameterized SQL queries are generated under the hood for all repository lookups, filtering, and mutations.

### Negative / Trade-offs
- **Learning Curve:** SQLAlchemy 2.0 query syntax (`select(Model).where(...)`) differs from legacy 1.x session query syntax, requiring disciplined code review to prevent legacy anti-patterns.
- **Migration Verification Discipline:** Autogenerated Alembic migrations must always be reviewed by engineers to verify table constraints and index definitions before merging.
